# ออกแบบระบบแยกรายรับ-รายจ่ายจากสลิป (Direction Engine)

> สถานะ: ใช้งานจริงบน production · อัปเดต 2026-09-26
> โค้ดหลัก: `src/services/slipParser.ts` (ชั้น 1-2), `src/handlers/webhook.ts` (ชั้น 3-4), `src/db/liff.ts` (ความจำ)

## ปัญหาพื้นฐาน

สลิปโอนเงินไทย 1 ใบ บอกว่า "A โอนให้ B จำนวน X บาท" แต่**ไม่บอกว่าใครคือเจ้าของสมุดบัญชี** สลิปของเราเอง (รายจ่าย) กับภาพหน้าจอที่คนอื่นโอนให้เรา (รายรับ) มีข้อความหน้าตาเหมือนกันทุกประการ หัวสลิป "โอนสำเร็จ" ปรากฏบนทั้งสองกรณี จึง**ห้ามเดาจากคำบนสลิปเพียงอย่างเดียว**

หลักการออกแบบ: **แถวที่ผิดจะไม่มีสิทธิ์ถูกเขียนลงสมุด** — ถ้าระบบวางใจทิศทางไม่ได้ ต้องถามผู้ใช้ด้วยการแตะครั้งเดียว แทนการบันทึกผิดแล้วให้ผู้ใช้ตามแก้

## บันไดการตัดสิน 4 ชั้น (Trust Ladder)

สลิปเข้ามา → ผ่าน pipeline: ดาวน์โหลดรูป → Typhoon OCR → **Parser กฎ (ฟรี)** → Gemini (เฉพาะเคส parser หลุด) → ได้ `extraction` ที่มี `amount, date, merchant, direction (เดาจากคำ), party_from, party_to` → ประมวลผลบันไดนี้:

```
ชั้น 1  ตรวจโครงสร้างสลิป
        ├─ ใบเสร็จ/QRจ่ายร้าน (ไม่มีบรรทัด "จาก/ถึง") → รายจ่าย แน่นอน ✅ บันทึกเลย
        └─ สลิปโอน (มีชื่อสองฝั่งหรือฝั่งเดียว) → ไปชั้น 2

ชั้น 2  กฎชื่อตัวเอง (self-name) — สัญญาณแรงสุด
        ├─ party_to  ≈ ชื่อเรา → รายรับ ✅ บันทึกเลย
        ├─ party_from ≈ ชื่อเรา → รายจ่าย ✅ บันทึกเลย
        └─ ไม่เจอชื่อเรา → ไปชั้น 3

ชั้น 3  ลายเซ็นเลขบัญชี (account-tail signature) — deterministic ที่สุด
        ├─ เลขท้ายบัญชีฝั่ง "ถึง" ตรงกับของเรา (จากความจำ) → รายรับ ✅
        ├─ เลขท้ายบัญชีฝั่ง "จาก" ตรงกับของเรา → รายจ่าย ✅
        └─ ไม่ตรง / ยังไม่มีเลขในความจำ → ไปชั้น 4

ชั้น 4  ความจำคู่กรณี (payer memory)
        └─ party_from ตรงกับชื่อที่เคย "โอนให้เรา" (บทบาท income) → รายรับ ✅

ชั้น 5  Trust Gate — ประตูกันความผิดพลาด
        ├─ สลิปโอนที่ชื่อสองฝั่งไม่ใช่เราและไม่อยู่ในความจำ → ❗ไม่บันทึก
        │   ส่งการ์ดสีส้ม "ยืนยันประเภทรายการ" ปุ่ม [เป็นรายรับ] [เป็นรายจ่าย]
        ├─ สลิปโอนมีชื่อฝั่งเดียว (ไม่ใช่เรา) + กฎเดาว่า "รายจ่าย" → ❗ถามเช่นกัน
        │   (เคสนี้คือภาพหน้าจอโอนของคนอื่นที่หัวสลิปเขียน "โอนสำเร็จ")
        └─ กฎเดาว่า "รายรับ" → ปล่อยผ่านบันทึก (รายรับจากคำ "เงินเข้า" ผิดยาก)
```

**ทำไมเลขท้ายบัญชีถึงแม่นกว่าชื่อ:** ตัวเลขไม่สะกดเพี้ยนเหมือนชื่อคนไทยใน OCR และเจ้าของบัญชีใช้เลขบัญชีเดิมทุกสลิปจากแอปตัวเอง (ธนาคาร mask เป็น `x1234` = 4 ตัวท้ายเสมอ) ระบบจึงเรียนรู้ "เลขท้ายบัญชีของเรา" จากสลิปรายจ่าย 1-2 ใบแรก (เก็บเป็น `contact_names` บทบาท self ในรูป `acc:1234`) หลังจากนั้นสลิปโอนทุกใบเทียบเลขท้ายฝั่งจาก/ถึงได้ทันที — แม้ชื่อ OCR เพี้ยนก็ตาม ส่วนเลขเต็ม (`1234567890`) ถูก normalize เป็น 4 ตัวท้ายเพื่อให้เทียบกับ mask ได้

หลังผ่านชั้น 1-3 ยังมีด่านกันซ้ำ (content dedup), โอนข้ามบัญชี (ชื่อบน=ล่าง → ไม่บันทึก), และ batch window ก่อนเขียนจริง

## โครงสร้างข้อมูล

### ตาราง `contact_names` — ความจำชื่อ 3 บทบาท (migration 007)

| PK | type | ความหมาย | เกิดจาก |
|---|---|---|---|
| (user_id, name, **expense**) | ร้าน/คนที่เราเคยจ่ายให้ | ใช้ reuse หมวด | บันทึกสลิปรายจ่าย / กดแก้เป็นรายจ่าย |
| (user_id, name, **income**) | คนที่เคยโอนให้เรา | ใช้ชั้น 3 | บันทึกสลิปรายรับ / กดแก้เป็นรายรับ |
| (user_id, name, **self**) | ชื่อของเจ้าของบัญชีเอง | ใช้ชั้น 2 | คำสั่ง `ชื่อบัญชี X`, เรียนรู้จากฝั่ง "จาก" ของสลิปรายจ่าย / "ถึง" ของสลิปรายรับ |

ชื่อเดียวกันมีได้หลายบทบาทพร้อมกัน (จ่ายให้เขาประจำ + เขาก็โอนคืนบ้าง) — ไม่ทับกัน

### คีย์ใน `slip_dedup_cache`
- `msg:<messageId>` — ผลวิเคราะห์ของข้อความนั้น (กัน LINE redelivery + ให้ปุ่ม confirm/dup อ่านย้อนหลัง)
- `img2:<sha256>` — ผลวิเคราะห์รูปไบต์เดิม (TTL 24 ชม.; prefix `img2:` เพื่อไม่ให้ผลเก่าก่อนอัปเกรด shadow ระบบ)
- `saved:<messageId>` — เครื่องหมายกันกดปุ่มยืนยันซ้ำสองรอบ

## วงจรเรียนรู้ (สำคัญที่สุด)

ระบบแม่นขึ้นเองจาก 3 ทาง:

1. **บันทึกอัตโนมัติ** — ทุกสลิปที่เซฟ ระบบจดบทบาทชื่อ (ฝั่ง "จาก" ของสลิปรายจ่าย = ชื่อเรา → self, ฝั่ง "ถึง" = คู่กรณี → expense ฯลฯ)
2. **การแก้ด้วยปุ่ม** (`set_type` / `confirm_type`) — เมื่อผู้ใช้กดแก้ทิศทาง คำตอบของผู้ใช้คือ ground truth: รายรับ → "ถึง" ถูกจดเป็น self, "จาก" จดเป็นผู้โอน (income); รายจ่าย → กลับกัน ครั้งต่อไปชื่อเดิมจะผ่านชั้น 2-3 อัตโนมัติ
3. **คำสั่ง `ชื่อบัญชี [ชื่อ]`** — ลงทะเบียนชื่อตัวเองแบบตายตัว (ใส่ได้หลายชื่อ/หลายรูปแบบสกุล) เป็นสัญญาณแรงสุดทันทีโดยไม่ต้องรอเรียนรู้

การเทียบชื่อใช้ `normalizeName`: ตัดคำนำหน้า (นาย/นาง/คุณ/ว่าที่ ฯลฯ), ตัดช่องว่าง-เครื่องหมาย, lowercase, แล้วเทียบเท่ากันหรือชื่อสั้นซ้อนในชื่อยาว (≥4 ตัวอักษร)

## ข้อจำกัดที่ยอมรับไว้

- OCR สะกดชื่อเพี้ยน → เทียบไม่เจอ → ตกไปชั้น 4 (ถาม) แทนที่จะเดาผิด — ตอบครั้งเดียวจบ
- กลุ่มที่เพื่อนจ่ายแทน (สลิป "จากเพื่อน ถึงร้าน") — ผู้ใช้ที่ต้องการจดเป็นรายจ่ายร่วม กดปุ่ม "รายจ่าย" ครั้งแรก ระบบจะเรียนรู้ว่าเพื่อนคนนี้จ่ายแทนได้ (บทบาท self ของเพื่อนจะไม่ถูกจด เพราะเจ้าของบัญชีเป็นคนตัดสินเอง)
- สลิปที่ OCR ไม่พิมพ์ชื่อใดเลย → กลับไปเดาจากคำหัวสลิป (รับความเสี่ยง เพราะไม่มีสัญญาณอื่นให้ใช้)

## ทางเลือกอนาคต (เมื่อต้องการแม่น 100% โดยไม่แตะปุ่ม)
